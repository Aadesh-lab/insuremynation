# InsureMyNation assistant — user flow

## Status: the replacement has landed

The CRM-connected assistant this document was written for now exists, and the site talks to
it. `frontend/src/components/chat/chatBackend.js` chooses:

| `CHAT_BACKEND` | what runs |
| --- | --- |
| `'orchestrator'` **(live)** | imagine.bo's headless API, called direct from the browser. See `HEADLESS_CHAT_INTEGRATION.md` and `useHeadlessChat.js` |
| `'proxy'` | our own `/v1/*` Go service, the funnel below, no lead capture. Kept as the rollback |

**Three things moved to their side:** the funnel questions, the system prompt, and the lead
capture. Their assistant asks for a name and mobile **once**, at the end, with a consent line,
and writes the lead to the CRM — so:

- **§6 below is superseded.** No `POST /v1/lead` is needed; do not build one, and do not add a
  contact form of our own anywhere in the panel. The lead is captured either way and the
  visitor would be asked twice.
- **§4 and §7 still stand** as the record of what our own funnel and proxy do, because the flag
  can still select them. §5 describes the proxy path's errors; the orchestrator path's are in
  the integration guide.

Their funnel turned out to be near-identical to the one below, down to the escape hatch
("Elsewhere in India - I will pass the city to the adviser"), so the flow a visitor walks is
substantially the same as what §3 describes. What differs: **no streaming** (one request, one
whole reply), **no history sent** from our side, and chips are parsed out of `- ` lines in the
reply rather than driven by `journeys.js`.

Two live findings worth carrying, both raised with them:

- **The domain allowlist does not gate `/widget-proxy/init`.** A request with
  `Origin: https://evil.example` created run 5645 and executed a model turn. Combined with
  "nothing is rate-limited on this path" in their §Things that will bite you, the public widget
  token is the only thing in front of a billed endpoint.
- **`context_variables.product` is not honoured.** `/?product=life` sent with `product: "life"`
  still opened the generic "Which cover are you looking for?" (run 5648), where their guide says
  it "wins over `page`". Our client sends it exactly as documented; the resolution is theirs.

## What our own assistant does (the `'proxy'` path)

Everything below describes `CHAT_BACKEND = 'proxy'`: turn by turn, verified against the live
knowledge base.

Read it with `frontend/src/components/chat/journeys.js` (the funnels) and
`backend/internal/services/chat.go` (`productPrompts`, the per-page instructions) open.

---

## 1. The parts

| part | file | job |
| --- | --- | --- |
| launcher + panel | `frontend/src/components/chat/ChatWidget.jsx`, `ChatPanel.jsx` | UI. Mounted once, outside `<Routes>`, so it survives navigation |
| funnels | `frontend/src/components/chat/journeys.js` | per-product questions, chip labels, the message each chip sends, and the CRM field each answer maps to |
| transport | `frontend/src/components/chat/useChat.js` | sessions, history, SSE, error bodies, product lock |
| proxy | `backend/internal/services/chat.go`, `sessions.go` | holds the RAG API key, pins `kb_id`/`system_prompt`/`top_k`/`temperature`, per-IP caps |
| corpus | `frontend/kb-corpus.txt` | the site's own copy, generated by `frontend/scripts/export-kb.mjs`, ingested into the RAG KB |

The browser never talks to imagine.bo. It calls this site's own `/v1/*`, same origin.

## 2. Entry points

Ads run per product line, so the page a visitor lands on already tells us which cover they
came for. That is the whole basis of the flow.

| how they arrive | what the assistant opens with |
| --- | --- |
| ad → `/health-insurance` (and the five other product pages) | that product's funnel, question 1 |
| ad → `/?product=health` (a home-page landing with the product in the URL) | same — the query parameter wins over the path |
| organic → `/`, `/about`, `/contact`, `/claim-support`, `/career` | "Hi! Which cover are you looking for?" and six product chips. Tapping one enters that funnel at question 2 **without a navigation** |
| any page, visitor types instead of tapping | free conversation against the corpus; no funnel |

`productForPage(pathname, search)` in `journeys.js` resolves this. An unrecognised
`?product=` value is ignored, not trusted.

The panel does **not** auto-open. On paid traffic an uninvited panel over the hero reads as a
popup and costs the page the ad paid for. The launcher sits bottom-right; the funnel is ready
the moment it is tapped.

## 3. The flow, step by step

**Step 0 — page load.** Nothing happens. No session is minted, no request is sent. A visitor
who never opens the panel costs nothing.

**Step 1 — visitor taps the launcher.** `chat.init()` runs once:

- If `sessionStorage` holds `imn-chat-session-id`, `GET /v1/sessions/{id}` restores the
  transcript. A 404 (expired, or now belongs to another client) silently starts fresh.
- Otherwise `POST /v1/sessions` mints one. **If this fails the panel still works** — `/v1/query`
  accepts an empty `session_id`; the conversation just isn't persisted server-side.

The panel renders the funnel's greeting locally. It is never sent to the model — which is why
every chip message below is a complete sentence that stands on its own.

**Steps 2–6 — the five questions.** Each is one round trip:

1. Visitor taps a chip (or types). The panel appends their message and an empty streaming
   assistant bubble.
2. `POST /v1/query` with `{message, history, session_id, product, stream: true}`. `history` is
   the last 10 turns *before* this one; `product` is an **id**, never prompt text.
3. Server side, per turn: validate (1–2000 chars), charge the per-IP cap, drop `session_id` if
   the caller doesn't own it, then set `kb_id`, `top_k: 5`, `temperature: 0.2` and
   `system_prompt = base + productPrompts[product]`. An unknown product id gets the base
   prompt — the map lookup *is* the allowlist.
4. Answer streams back as SSE. `chunk_text` and `file_id` are stripped from sources on the way
   through; the panel ignores sources entirely.
5. The chip row advances. **The step is the count of visitor messages** — it stays aligned with
   what the assistant just asked only because the product prompt pins the question order.

**Step 7 — the close.** The fifth answer is followed by a summary of all five and a hand-over:
fill the quote form on this page for a call back, or call `+91 99101 69789`. That reply must
not contain a question. The chip row disappears — `journey.steps[5]` is undefined — leaving a
free composer.

**Any point — the visitor goes off script.** Asks a question instead of answering: the
assistant answers from the corpus and repeats its question. Asks for a human: it hands over
immediately and stops asking. Navigates to another product page mid-funnel: **the product is
frozen on the first message**, so the funnel does not switch rails; **New chat** in the header
clears it and re-resolves from the current page.

## 4. The funnels

Five questions each, in this order. `field` is the CRM key, and the values are the ones a chip
produces — a typed answer has to be normalised to the same set (see §6).

**health** — `members` (self · self-spouse · family-floater · parents) → `eldest_age` (18-35 ·
36-50 · 51-60 · 60-plus) → `city` (delhi-ncr · mumbai · bengaluru · other) → `sum_insured` (5L
· 10L · 25L · 1Cr-plus) → `existing_cover` (employer · own-policy · none · **ped**)

**life** — `plan_type` (term · term-savings · ulip · unknown) → `age` (25-30 · 31-40 · 41-50 ·
50-plus) → `sum_assured` (50L · 1Cr · 2Cr · 5Cr-plus) → `liabilities` (home-loan ·
personal-loan · business · none) → `dependents` (spouse · spouse-kids · spouse-kids-parents ·
parents)

**car** — `policy_status` (renewal · new-vehicle · expired · third-party) → `segment` (mass ·
suv · luxury · exotic) → `rto_city` → `ncb` (no-claim · claimed · first-policy · unknown) →
`addons` (zero-dep · engine · rti · unknown)

**bike** — `engine_class` (superbike · mid · commuter · electric) → `policy_status` →
`rto_city` → `ncb` → `addons` (zero-dep · accessories · pillion · engine)

**travel** — `destination` (schengen · usa-canada · uk · gulf-sea) → `trip_type` (single ·
multi-trip · student · family) → `duration` (lt-15d · 15-30d · 1-6m · gt-6m) → `travellers`
(self · self-spouse · family · **senior**) → `visa_proof` (required · have-visa ·
not-required)

**marine** — `movement` (import · export · domestic · both) → `mode` (sea · air · surface ·
multimodal) → `commodity` (machinery · electronics · textiles · chem-pharma) → `policy_type`
(single-transit · open-cover · unknown) → `value` (lt-50L · 50L-5Cr · gt-5Cr · turnover)

Three properties of these that are load-bearing, and each was a bug before it was a rule:

- **Chips send answers, never questions.** The corpus is the site's own marketing copy: it has
  no family floater, no lakh/crore, no waiting periods, no NCB rules. A chip phrased as a
  question retrieves nothing and the visitor gets "I don't have that information".
- **Each message closes its question.** "We are in another city" reads as a deferral, so the
  assistant asks *which* city — and from then on the chip row is a step behind and the visitor
  answers questions that were never asked. Escape hatches say where the detail is going
  instead: *"elsewhere in India; I will give the city to the adviser."*
- **The lists are flat, with no branching.** Composition lives in the label ("Me, spouse +
  kids"), not in a follow-up count.

### What the assistant will not do

Pinned in `funnelRules`, and both restrictions are about not lying to a visitor:

- **No premium, rate, waiting period or eligibility decision.** None of it is in the corpus,
  so any figure would be invented and quotable back at the firm.
- **No asking for a name, phone, email, PAN, Aadhaar or policy number.** Nothing in this repo
  captures a lead today. A number typed into the chat lands in the upstream's transcript table
  and is read by nobody, so asking for one promises a call back that will not happen.

**That second rule is the one lead capture changes.** It must not be relaxed before the
endpoint that catches the answer exists.

## 5. What the visitor sees when something breaks

The panel reads the backend's error body, which is deliberate — these are distinguishable, and
the hosted widget we replaced flattened them all to "Something went wrong."

| condition | shown | retry helps? |
| --- | --- | --- |
| per-IP cap (30/10 min, 150/day) | "Too many messages. Please try again in a few minutes." | later |
| upstream 402, conversations exhausted | "The assistant is busy right now. Please try again later." | later |
| `RAG_API_KEY`/`RAG_KB_ID` unset | "chatbot not configured" | no |
| upstream 5xx / transport | "chatbot unavailable" | maybe |
| stream ends empty | "I don't have an answer for that. Please try rephrasing." | yes |

A failed turn is removed from the transcript and the text handed back, so a rate-limited
visitor retries without retyping. Every non-rate-limit error also shows the phone and email.

Session and privacy: **`sessionStorage`, not `localStorage`** — people ask this assistant about
health conditions and money, and localStorage handed the transcript to the next person on a
shared machine. Refresh keeps the thread; closing the tab drops it. Session ownership is keyed
to client IP server-side with a 24h TTL.

## 6. Lead capture — SUPERSEDED

**Do not build this.** The orchestrator captures the lead itself (see Status, above): name and
mobile once at the end, with a consent line, straight into the CRM. This section is kept only
as the record of what the requirement was, and because the field vocabulary in §4 is still what
a lead should be segmented on.

What is still worth reading here: the notes on normalising typed answers to the chip
vocabulary, on a partial funnel being a lead, and on `landed_from` — that last one is ours to
get right, and `frontend/src/components/chat/pageContext.js` now does, first-seen per tab.

The funnel exists to produce a qualified lead. On the `'proxy'` path it produces one and throws
it away: five structured answers, on the page for the product they want, and nothing catches
them.

### The object to capture

`journeys.js` already carries `field` per step and `value` per chip for exactly this. After a
completed funnel the panel holds enough for:

```json
{
  "product": "health",
  "qualification": {
    "members": "family-floater",
    "eldest_age": "36-50",
    "city": "delhi-ncr",
    "sum_insured": "10L",
    "existing_cover": "ped"
  },
  "contact":  { "name": "…", "phone": "+91…", "email": "…" },
  "consent":  { "given": true, "text": "…exact wording shown…", "at": "2026-08-14T09:12:44Z" },
  "context": {
    "page": "/health-insurance",
    "landed_from": "?utm_source=google&utm_campaign=health-delhi",
    "session_id": "…",
    "turns": 5,
    "started_at": "…", "completed_at": "…"
  },
  "transcript": [ { "role": "user", "content": "…" }, … ]
}
```

Notes that will otherwise be learned the hard way:

- **`qualification` values must stay the chip vocabulary.** A typed answer ("we're 4 in
  Gurgaon") has to be normalised to `family-floater`/`delhi-ncr` before it is stored, or the
  CRM ends up with free text nobody can segment on. Normalising is the model's job — return it
  as structured output alongside the reply, not by parsing prose later.
- **A partial funnel is still a lead.** Someone who answers two questions and leaves is worth
  more than nothing. Store what exists with a completeness marker rather than requiring five.
- **`landed_from` is the point of the whole exercise** — it is what ties a closed policy back
  to the ad that paid for it. Capture the full original query string on first load, not the
  current one, and keep it for the session.

### The endpoint

```
POST /v1/lead      (public, same origin, no auth — same trust model as /v1/query)
  201 {"lead_id": "…"}
  429 {"error":"Too many submissions. Please try again later."}
  503 {"error":"lead capture not configured"}
```

Requirements, in the order they will bite:

1. **Its own cap, keyed on `c.ClientIP()`** like `allowIP` — reuse `allowN` in `chat.go`.
   Something like 5 per 10 minutes and 20 a day. This is the only abuse control; a public form
   that writes to a CRM is a spam target.
2. **Idempotency.** The browser retries. Key on `session_id` + `product` and update rather
   than insert, or the sales desk gets the same person four times.
3. **Validate at the boundary.** Indian mobile shape, email shape, name length. Reject rather
   than forward garbage into the CRM.
4. **Never store PAN, Aadhaar or card details**, and keep the prompt's ban on asking for them.
   The funnel needs none of it and holding it changes what a breach means.
5. **Consent is explicit and recorded** — the exact wording shown, and when. Storing an Indian
   resident's contact details for marketing engages the DPDP Act; have the wording and the
   retention period confirmed by whoever owns compliance, and record the text actually
   displayed rather than a version number.
6. **A CRM outage must not lose the lead or break the chat.** Write it locally first, then push
   asynchronously with retries. The visitor's reply must not wait on the CRM, and a failed
   push must be visible — a lead that silently vanished is worse than a visible error.
7. **Never log the contact block.** The existing rule is that the RAG key never appears in a
   log line; phone numbers get the same treatment.

### Where it goes in the conversation

The close (§3, step 7) becomes: summary → *"want an adviser to call you back?"* → on yes, ask
for name and mobile **in that one turn, nothing more** → confirm → `POST /v1/lead`. On no,
today's hand-over text. The quote form on the page stays as the alternative; it is not
replaced.

Two turns, not five. The qualification is already done; asking for contact details is the ask
that loses people, so it comes last and only once.

### CRM mapping

Left open deliberately — the target CRM is not chosen. Whatever it is, the mapping needs:
`product` → pipeline or lead source; `qualification` → custom fields, one per key above, using
the chip vocabulary as the picklist; `context.landed_from` → campaign attribution;
`transcript` → a note on the record, so the adviser opens the call knowing what was said.

Flag on the record whichever of these applies — they change who should call and how fast:
`existing_cover: ped` (health), `travellers: senior` or `visa_proof: required` (travel),
`policy_status: expired` (car, bike), `value: gt-5Cr` (marine), `sum_assured: 5Cr-plus` (life).

## 7. What the replacement must not drop

Everything here survives a rewrite of the UI. Each of these was a bug once.

1. **The RAG API key never reaches the browser.** The only reason the Go service exists.
2. **`kb_id`, `system_prompt`, `top_k`, `temperature` are set server-side.** A visitor cannot
   retarget a query. The product hint is an **id looked up in an allowlist** — browser text
   never reaches `system_prompt`.
3. **`chunk_text` and `file_id` are stripped from sources**, plain and streaming both.
4. **`/v1/kb` and `/v1/sessions` are narrowed** to the one KB and to the caller's own sessions.
5. **The per-IP cap keys on a header the edge overwrites** (`CLIENT_IP_HEADER=X-Real-Ip` on
   Railway). Naming a header the edge does *not* set is worse than leaving it blank: every
   caller can then claim any IP.
6. **Error bodies reach the visitor.** A rate limit must not look like a crash.
7. **Transcripts are per-tab** (`sessionStorage`), for the shared-computer case.
8. **No invented premiums, and no asking for contact details you cannot store.**

## 8. Open items

- **The orchestrator's `init` is not origin-gated and not rate-limited** — see Status. Theirs to
  fix; a browser-side cap would be protection that is not there, since anyone can call the
  endpoint with `curl`.
- **`context_variables.product` is ignored**, so a `/?product=…` ad landing gets the generic
  opener. Theirs to fix. A one-line workaround exists on our side — send the product page's
  pathname as `page` — but it would put a URL the visitor never visited into their reporting,
  so it is not being done without their say-so.
- **No lead capture on the `'proxy'` path** — §6. Only matters if the flag is rolled back.
- **`frontend/src/data/site.js:12` states a different office address** from `Contact.jsx`
  (Arunachal Building / Barakhamba Road vs Ambadeep Building / Kasturba Gandhi Marg), so the
  live site shows both. The corpus uses the Contact page's.
- **The step index is positional.** It stays aligned because the product prompt pins the
  question order. If it ever drifts, have the model name the step it is on and key off that.
- **The corpus has no product facts beyond the site's copy** — no waiting periods, no
  clause-level detail. Everything specific still needs an adviser, and the prompt says so.
